# 저장 백엔드 전환 계획 (로컬 SaveGame → 서버 권위)

## 이 문서의 범위

이 문서는 **아직 구현되지 않은 전환 계획**의 단일 출처다. 단계 정의, 순서 근거, 백엔드 선택 근거, 미리 확정한 설계 결정을 담는다.

현재 코드의 저장 구조·슬롯 영역·레이드 신뢰 경계는 [ItemSaveNetworkStructure.md](ItemSaveNetworkStructure.md)가 단일 출처다. 이 문서는 그 값이나 구조를 복사하지 않고 링크로 참조한다.

**현재 구현 상태: 0단계(계획만).** 아래 1~3단계 중 착수된 것은 없다.

### 출시 방침과의 관계 (중요)

> **출시는 로컬 `SaveGame` + Steam Cloud로 간다.** 이 문서의 서버 권위 전환은 **학습 목적**이며 출시 방침이 아니다.

이 문서를 읽고 "출시 전에 3단계까지 끝내야 한다"고 오해하지 말 것. 출시 기준 신뢰 경계는 [ItemSaveNetworkStructure.md](ItemSaveNetworkStructure.md)에 적힌 현재 구조 그대로다.

이 판단이 합리적인 근거: LostSignal은 PvP가 없는 3인 코옵 익스트랙션이다. 세이브 조작의 피해는 조작한 본인과 같이 뛰는 인원에게만 미치고, 공개 경제나 랭킹을 오염시키지 않는다. 아래에 적은 서버 권위의 근거(밴 회피 비용, 아이템 복제 차단)는 PvP나 공유 경제가 있을 때 무게가 생기는 것들이다.

따라서 아래 단계 계획은 **어디까지 공부하고 멈출지 고르는 메뉴**로 읽는다. 1단계는 출시 코드에도 그대로 남는 구조 정리이고, 2a까지 하면 원격 저장 왕복(인증·토큰·비동기 로드·충돌 처리)을 익히며, 3단계는 데디케이티드 전환과 경제 명령 API가 통째로 묶여 있어 사실상 별개 프로젝트다.

## 문제 정의

현재 영구 저장은 각 클라이언트의 로컬 `SaveGame` 파일이다. 즉 로비 진행 데이터(인벤토리·창고·골드·칩)는 파일을 고치면 그대로 위조된다. 레이드 **중**에는 서버가 확정하지만, 레이드 **입장 시 제출 데이터**는 어쩔 수 없이 신뢰하는 구조다.

목표는 이 신뢰 경계를 "레이드 중에만 서버"에서 "영구 데이터도 서버"로 옮기는 것이다.

### Steam Cloud는 조작 방지가 아니다 (이식성 수단이다)

출시에 Steam Cloud를 쓰기로 정했으므로, **무엇을 얻고 무엇을 못 얻는지**를 명확히 해둔다. 얻는 것은 PC 무관 이식성과 백업이고, 못 얻는 것은 조작 방지다.

Steam Cloud의 신뢰 수준은 로컬 파일과 **동일하다.**

- 파일은 `Steam/userdata/<steamid>/<appid>/`에 평문으로 놓이고 유저가 고칠 수 있다. Steam은 고쳐진 파일을 그대로 업로드한다. 클라우드에 있다는 게 검증됐다는 뜻이 아니다.
- `ISteamRemoteStorage::FileWrite`로 명시적으로 써도 같다. 데이터가 클라이언트 프로세스에서 나오는 한 그 프로세스를 장악한 쪽이 내용을 정한다.
- 암호화도 답이 아니다. 키가 클라이언트에 함께 배포된다.
- **충돌 해결이 추가 취약점이다.** 기기 간 충돌 시 Steam은 어느 쪽을 쓸지 유저에게 묻는다. A기기에서 아이템을 쓴 뒤 클라우드의 옛 버전을 선택하면 아이템이 복제된다.

**출시 방침에서는 이게 문제되지 않는다.** 권위가 여전히 하나이기 때문이다 — 로컬 파일이 유일한 진실이고 Steam Cloud는 그 파일의 운반·백업 수단일 뿐이다. 아래 "권위는 하나" 원칙을 깨지 않는다.

다만 감수하는 리스크는 명시해둔다.

```text
감수    세이브 파일 직접 편집으로 인벤토리/골드 위조 가능
감수    기기 간 충돌에서 옛 버전을 선택해 아이템 복제 가능
무관    PvP·공유 경제가 없으므로 타인 피해 없음
```

반대로, **서버 권위 구조로 갈 경우엔 Steam Cloud에 진행 데이터를 올리면 안 된다.** 그 순간 권위가 둘이 되고 위 복제 경로가 되살아난다. 그 세계에서 Steam Cloud에 올릴 것은 키바인딩·오디오·그래픽 같은 설정값뿐이고, PC 무관 이식성은 Steam Cloud가 아니라 Steam Auth(신원)가 해결한다.

### 출시 시 Steam Cloud 실무 항목

학습용 전환과 무관하게, 출시 전에 실제로 해야 하는 작업은 이쪽이다.

```text
- Steamworks 파트너 사이트에서 Auto-Cloud 파일 경로 패턴 등록
  대상: UE SaveGame 경로 (Saved/SaveGames/*.sav)
- 유저별 쿼터와 파일 개수 제한 확인 (세이브 크기는 작으므로 여유 있음)
- 충돌 발생 시 유저에게 보여줄 안내 (어느 쪽이 최신인지 판단 근거)
- 디버그 json 산출물은 Cloud 대상에서 제외 (ULSSaveSubsystem::SaveDebugJson)
```

마지막 항목을 놓치면 불필요한 파일이 동기화되고 쿼터를 잡아먹는다.

## 확정한 설계 원칙

### 1. 백엔드는 여러 개, 권위는 하나

로컬 백엔드와 원격 백엔드를 **인터페이스 수준에서만** 이중화한다. 저장소의 권위를 이중화하면 안 된다.

```text
허용   인터페이스 이중화 (ILSSaveBackend → Local / Remote 구현)
금지   권위 이중화 (로컬도 쓰고 원격도 쓰고, 끊기면 폴백)
```

- **부팅 시 1회 결정되고 세션 중 절대 바뀌지 않는다.**
- **원격 실패 시 로컬 폴백 금지.** 재시도하고, 안 되면 에러를 표시한다. 폴백하는 순간 권위가 둘이 된다.
- 오프라인 프로필과 온라인 프로필은 왕복하지 않는다. 오프라인에서 얻은 것을 온라인 계정에 합칠 방법이 없다(익스트랙션 경제에서 머지는 성립하지 않는다).

### 2. 오프라인 모드는 개발용 전용

**이 원칙은 서버 권위 구조 안에서만 적용된다.** 출시 방침(로컬 + Steam Cloud)에서는 오프라인이 기본 동작이므로 해당되지 않는다.

서버 권위로 갈 경우: 패키징 빌드에서 오프라인을 차단한다. 서버 권위가 목표인 이상 출시 기능으로서의 오프라인은 성립하지 않는다(오프라인에서 얻은 것을 온라인 계정에 합칠 방법이 없다).

다만 개발용 경로는 **출시 후에도 영구히 남긴다.** 비프로그래머 팀원(아트 2 / 기획 3)이 인증 없이 에디터를 돌릴 수 있어야 하고, 에디터에서 Steam을 붙이는 건 매일 워크플로우를 갉아먹는다.

### 3. 동기 API는 유지한다

`ULSSaveSubsystem`의 읽기 API는 **한 줄도 바꾸지 않는다.** 현재 구조가 이미 "인메모리 `SaveData`가 진실, mutation은 동기, 그 뒤 저장 호출" 형태라 여기에 맞물린다.

```text
유지    GetInventory() 등 동기 반환 (호출 지점 500곳 이상이 무사)
변경    Save() → dirty 표시 + 경계에서 flush
신규    부팅 최초 로드와 레이드 결과 확정만 진짜 비동기
```

진짜 비동기가 되는 지점은 두 곳뿐이다.

1. **부팅 최초 로드** — 로그인 + 프로필 fetch 완료까지 대기. `HasExistingSave()`가 지금은 즉시 답하지만 원격에선 로그인 후에만 알 수 있어 타이틀에 "접속 중" 상태가 필요해진다.
2. **레이드 결과 확정 저장** — ACK 필요.

## 백엔드 선택

**관리형 Postgres 계열**(Supabase 등)을 권한다. 자체 DB 서버 구축은 하지 않는다.

### 왜 관리형인가

"데디케이티드 서버를 어차피 자체 운영하니 DB도 같은 부담"은 성립하지 않는다. 두 서버는 운영 성질이 다른 종류다.

| | UE 데디서버 | 영속 계층 |
|---|---|---|
| 상태 | 매치 단위, 사실상 stateless | 절대 잃으면 안 됨 |
| 크래시 | 레이드 1판 손실, 재시작하면 끝 | 전 플레이어 진행 소실 |
| 필요한 것 | 프로세스 관리, 인스턴스 스핀업 | 백업·복구·마이그레이션·접근 제어 |

**핵심 조건: 로비를 클라이언트 로컬로 유지하면 로비에는 서버 프로세스가 없다.**

현재 타이틀 → 로비는 `OpenLevel`이고, 로비 → 레이드만 `ServerTravel`이다. 즉 제작·창고·상점·칩 장착이 벌어지는 동안 붙을 서버 인스턴스가 없다.

> **주의:** `ServerTravel`은 리슨/데디케이티드 양쪽에서 쓰이므로 그것만으로 현재 넷모드를 판정할 수 없다. 현재 데디케이티드가 아니라는 근거는 따로 있다 — `Source/`에 `LostSignalServer.Target.cs`가 없어 서버 빌드 자체가 불가능하다. 자세한 현황은 [DedicatedServerBuildout.md](DedicatedServerBuildout.md)가 단일 출처다.

**이 문서(학습 범위)의 전제: 로비는 클라이언트 UI로 두고, 경제 권위는 백엔드 서비스가 갖는다.** 근거는 아래 `로비 경제 권위를 어디에 둘 것인가`에 정리했다.

> **출시 방침과 구분할 것.** 출시는 로비 경제도 클라이언트가 확정하고 영구 저장은 로컬 `SaveGame`이다([DedicatedServerBuildout.md](DedicatedServerBuildout.md)의 `E2 결정`). 아래 논의는 "서버 권위를 한다면"이라는 가정 안에서만 성립한다.

그 전제에서, 자체 호스팅을 고르면 선택지가 둘뿐이다.

```text
클라가 DB에 직접 붙는다     → DB 크리덴셜을 클라에 심어야 함. 불가
상시 켜진 API 서비스를 만든다 → 데디서버와 무관한 두 번째 서버 종류를 설계·배포·운영
```

즉 실제 선택지는 "관리형 DB vs 자체 DB"가 아니라 **"관리형 영속 계층 vs API 서버를 하나 더 직접 만들기"**다. 후자는 운영이 아니라 코드다 — 인증(티켓 검증, 토큰 발급/갱신/폐기), 프로필 read/write, 제작 RPC, 레이드 결과 커밋, 스키마 마이그레이션, TLS·시크릿 관리, 게임 서버와 별개인 배포 파이프라인.

### 관리형이 실제로 주는 것

1. **운영되고 반출되고 검증된 백업.** PITR 기능 자체는 MySQL(binlog)·PostgreSQL(WAL) 모두 엔진에 내장돼 있다. 차이는 기능 유무가 아니라 ① 주기적 풀 백업 스케줄 ② **호스트 밖으로 반출** ③ 복구 리허설이 돼 있는지다. 백업이 죽은 서버의 같은 디스크에만 있으면 백업이 없는 것과 같다.
2. **행 단위 접근 제어(RLS) + 컬럼 권한.** 3단계의 "클라 쓰기 권한 박탈"이 정책과 `GRANT` 몇 줄이 된다. 정확한 메커니즘 구분은 아래 `접근 제어 메커니즘` 참조.
3. **PostgREST가 CRUD HTTP 레이어를 대신한다.** UE는 `HTTP` + 이미 의존에 있는 `Json`만 쓰면 되고 libpq 링크가 없다.

**단, 3번은 "API 서버가 통째로 없어진다"는 뜻이 아니다.** 다음 두 가지는 관리형을 써도 직접 만들어야 한다.

```text
인증 교환 함수   Steam 티켓 검증 + 자체 세션/갱신 토큰 발급
                 PostgREST 는 티켓을 검증하지 않고 Supabase Auth 에 Steam 기본 공급자도 없다
                 Publisher Web API 키를 보관할 Edge Function 또는 별도 인증 서비스 필요 (2b단계)
경제 명령 API    제작·상점·창고·레이드 결과 커밋 검증 (3단계)
```

즉 정확히 말하면 **CRUD API는 없애주고, 인증 교환 함수 하나와 경제 명령 API는 남는다.** 2a단계까지는 이 논거가 강하게 성립하지만, **3단계로 갈수록 약해진다** — 서버 검증 로직이 늘어나면 결국 함수/RPC를 그만큼 쓰게 되기 때문이다. 다만 Edge Function 몇 개와 풀 API 서버(인증 + CRUD + RPC + 마이그레이션 + TLS + 배포 파이프라인)는 여전히 규모가 다르다.

### 정직하게, 약한 논거

- 벤더 락인은 낮다. 그냥 Postgres이고 `pg_dump`로 나온다.
- 규모가 커지면 VPS가 더 쌀 수 있다. 현재 규모(3인 MO)에선 양쪽 다 사실상 무료.
- 데디서버와 리전이 다르면 왕복이 붙지만, 영속 쓰기는 레이드 경계에서만 일어나 실질 영향은 작다.

### MySQL 계열을 고를 경우

PITR은 문제없지만 **RLS 대응물이 없어 API 레이어를 직접 써야 한다.** 그 경우 API 서버 작성이 2단계에 바로 들어온다고 보면 된다. Postgres를 권하는 이유는 PITR이 아니라 RLS + PostgREST다.

### PITR보다 원장이 일상 도구다

PITR은 DB **전체**를 특정 시점으로 되돌린다. "플레이어 A가 3시에 아이템을 잃었다"에 PITR을 쓰면 다른 모든 플레이어의 진행도 함께 날아간다.

```text
일상용   append-only 거래 원장 테이블
         - 누가 언제 무엇을 얻고 잃었는지
         - 특정 플레이어만 조회·복구 가능, 아이템 복제 버그 탐지에도 사용
재난용   PITR
         - 스키마 마이그레이션 실수, 대량 삭제
```

관리형이 편한 건 프로덕션을 건드리지 않고 시점 T의 복제 인스턴스를 띄워 필요한 행만 꺼내올 수 있다는 점이다.

## 미리 확정해두는 스키마 결정

둘 다 **지금 정하면 공짜, 나중에 하면 데이터 마이그레이션**이다.

### 신원과 프로필 분리

DB의 PK로 SteamID를 직접 쓰지 않는다.

```text
users(user_id PK, created_at, ...)
identities(user_id FK, provider, provider_id, UNIQUE(provider, provider_id))
profiles(user_id FK, server_owned jsonb, client_owned jsonb, updated_at)
```

이렇게 하면 세 가지가 동시에 해결된다.

- **2a단계가 버려지는 작업이 아니게 된다.** 개발용 인증이 `provider='dev'` 한 행, Steam이 `provider='steam'` 한 행이다. 2a에서 만든 세션 토큰·갱신·게이트 UI가 그대로 살아남는다.
- 개발용 경로를 출시 후에도 유지할 수 있다.
- 나중에 다른 스토어가 붙어도 마이그레이션이 없다.

### 프로필 컬럼을 소유자별로 쪼갠다

`jsonb` 한 덩어리로 넣으면 편하지만, 그러면 **부분 쓰기 금지를 걸 수단이 사라진다.** 컬럼 권한은 컬럼 단위로만 작동하고 jsonb 내부 필드에는 도달하지 못하기 때문이다. 통짜로 만들면 3단계에서 스키마 마이그레이션과 기존 데이터 이전이 추가로 붙는다.

### 접근 제어 메커니즘 (혼동 주의)

두 가지는 서로 다른 기능이고 **함께** 써야 한다.

```text
RLS (Row Level Security)   행 단위. "자기 user_id 행만 접근" 을 담당
                           컬럼 단위 제한 기능이 아니다
컬럼 권한                  GRANT UPDATE(client_owned) ON profiles TO <클라 역할>
                           server_owned 에 UPDATE 를 주지 않는 것이 실제 쓰기 차단
```

필요한 구성은 **"자기 행만 접근하는 RLS + `client_owned`만 UPDATE 가능한 컬럼 권한 + 권한이 제한된 서버 역할"**이다.

> **주의:** Supabase의 `service_role` 키는 RLS를 우회한다. 데디서버용 자격증명을 만들 때 `service_role`을 그대로 쓰면 접근 제어가 무의미해지므로, 필요한 테이블·컬럼에만 권한을 준 **전용 역할**을 따로 만든다.

### 필드 전수 분류

`ULSSaveGame`의 모든 `UPROPERTY`를 빠짐없이 분류한다. **누락된 필드는 원격 왕복에서 소실된다.** 필드 원본은 [LSSaveGame.h](../../Source/LostSignal/Session/LSSaveGame.h), 의미는 [ItemSaveNetworkStructure.md](ItemSaveNetworkStructure.md)의 `저장 영역`이 단일 출처다.

```text
server_owned
  Inventory
  WarehouseItems
  SafeStash
  EquipmentSlots
  ChipEquipmentSlots
  ChipSignalGaugePercent      신호 게이지 → 적재 프로토콜 → 인벤 용량. 경제에 직결
  Gold
  bGoldInitialized            ★ 아래 주의
  bRaidSaveActive
  ActiveRaidLoadout
  ActiveRaidConsumedItems

client_owned
  QuickSlots
  SkillLoadoutsByCharacter    FLSSkillLoadout{ SkillIDs[3], bInitialized } 포함

메타 (소유자 아님, 전송 DTO 가 관리)
  schema_version              신규. 아래 참조
  bInventoryMigrated          로컬 세이브 포맷 마이그레이션 플래그
  Stash / Player1Inventory    레거시. 최초 업로드 전 로컬에서 마이그레이션 후 전송 제외
```

**★ `bGoldInitialized` 주의.** 이 플래그가 원격 역직렬화에서 누락되면 `EnsureGoldInitialized()`가 매 로드마다 기본 골드를 다시 지급한다(로드 경로에서 호출된다). 소실되면 조용히 골드가 불어나는 종류의 버그라 발견이 늦다. 같은 성격의 "1회성 플래그"는 전부 같은 위험을 가진다.

**판단 보류 항목:** `SkillLoadoutsByCharacter`를 `client_owned`로 둔 것은 현재 스킬 **소유권**이 세이브에 없기 때문이다(선택 슬롯만 저장). 나중에 스킬 해금이 재화 소비가 되면 `server_owned`로 옮겨야 한다.

### 전송 DTO와 스키마 버전

`ULSSaveGame`을 그대로 직렬화하지 않고 **명시적 전송 DTO**를 둔다. 이유는 위 분류를 코드로 강제하기 위해서다 — 필드가 추가됐는데 분류를 안 하면 컴파일 단계나 리뷰에서 걸려야 한다.

```text
schema_version   프로필 JSON 의 포맷 버전
                 서버에 저장, 로드 시 현재 버전과 비교해 마이그레이션 분기
                 로컬 세이브의 bInventoryMigrated 가 하던 역할의 원격판
```

직렬화 자체는 여전히 싸다. 저장 필드가 전부 UStruct라 `FJsonObjectConverter`로 변환되고 `Json`/`JsonUtilities`는 이미 `Build.cs` 의존에 있다. **DTO 경계와 버전 필드를 두는 비용만 추가된다.**

스키마 정규화(jsonb → 관계형 테이블)는 3단계 경제 명령 API에서 필요해질 때만 한다.

### 동시성과 멱등성

원격 저장은 로컬 파일 쓰기와 달리 **동시 쓰기와 재시도**가 존재한다. `updated_at`만으로는 둘 다 막지 못한다.

```text
profile_revision   낙관적 잠금용 정수. 읽을 때 받은 값과 일치할 때만 UPDATE 성공
                   불일치 = 다른 세션이 먼저 썼다는 뜻 → 재읽기 후 재시도 또는 거절
                   막는 것: 두 클라이언트 동시 접속 시 나중 쓰기가 앞 쓰기를 덮는 사고

raid_id            레이드 결과 커밋의 멱등 키. 같은 raid_id 는 한 번만 반영
                   막는 것: DB 응답이 유실돼 서버가 재시도할 때 보상이 두 번 지급되는 사고
```

두 번째가 특히 중요하다. 3단계에서 레이드 결과를 서버가 커밋하는 순간, 네트워크 타임아웃 후 재시도는 **정상 동작**이고 중복 지급은 그 정상 동작의 부작용이다. 멱등 키 없이는 재시도를 안전하게 할 수 없다.

## 단계 계획

각 단계는 그 자체로 "게임이 돌아가는 상태"에서 끝난다. 중간에 멈춰도 문제가 없도록 잘랐다.

| 단계 | 한 줄 요약 | 끝나면 얻는 것 | 신뢰 수준 |
|---|---|---|---|
| **1** | 저장 경로를 인터페이스 뒤로 숨김 (백엔드는 여전히 로컬 파일) | 백엔드 교체 가능 상태 | 변화 없음 |
| **2a** | 관리형 DB에 프로필 저장, 인증은 개발용 | PC 바뀌어도 같은 계정 | 로컬과 동급 (조작 가능) |
| **2b** | 신원을 Steam으로 교체 | 진짜 계정, 밴이 의미를 가짐 | 신원 확보 |
| **3** | **모든 영속 경제 변경을 서버 명령 경유로** (레이드 결과 + 로비 제작·상점·창고·장착) | 아이템·골드 위조 차단 | 경제 서버 권위 |

### 3단계는 쪼갤 수 없다 (설계 정정)

이전 판에서는 3단계(레이드 결과만 서버 권위)와 4단계(로비 변경도 서버 검증)를 나누고 4단계를 선택으로 뒀다. **그 분할은 성립하지 않는다.**

로비의 제작·창고·상점·장착이 `Inventory`·`WarehouseItems`·`EquipmentSlots`·`Gold`를 직접 바꾸는데, 이 필드들이 곧 레이드 산출물이 기록되는 자리다. 따라서

```text
클라 쓰기를 막으면    → 로비 기능이 저장되지 않는다
클라 쓰기를 허용하면  → 레이드 보상을 클라가 덮어쓸 수 있다
```

두 번째가 핵심이다. **DB 입장에서 "정당한 제작 결과 쓰기"와 "위조된 레이드 보상 쓰기"는 구분 불가능한 같은 UPDATE다.** 레이드 중/밖을 시간대로 가르는 것도 소용없다 — 로비 상태로 쓰면 그만이기 때문이다.

즉 레이드 결과만 서버 권위로 만들면 **아무 보장도 얻지 못한다.** 경제를 바꾸는 모든 경로가 동시에 서버 명령이 되어야 비로소 "위조 불가"가 성립한다. 그래서 둘을 3단계 하나로 합친다. 이것이 3단계가 크고 마지막인 이유다.

### 1단계 — 저장 경로 추상화

현재 `ULSSaveSubsystem`은 인메모리 `SaveData`를 고친 뒤 곧바로 로컬 파일에 쓴다. `Save()`가 서브시스템 내부 30여 곳에서 즉시 호출된다.

```text
변경 전   mutation → SaveData 수정 → Save() → 즉시 파일 쓰기
변경 후   mutation → SaveData 수정 → MarkDirty() → 백엔드에 위임
                                                   Local  : 즉시 flush (현행 유지)
                                                   Remote : 코얼레싱 후 경계 flush
```

**코얼레싱은 원격 백엔드에만 적용한다.** 1단계에서 로컬 백엔드까지 지연 쓰기로 바꾸면 안 된다.

- 코얼레싱의 동기는 원격 쓰기 과금과 왕복 비용이다. 로컬 파일 쓰기에는 그 동기가 없다.
- 지연 쓰기는 **내구성을 바꾼다.** 현재는 mutation 직후 동기 저장이라 크래시해도 직전 변경까지 남지만, 경계 flush로 바꾸면 경계 이전의 변경분이 사라진다. 이건 "동작 diff 0"이 아니라 명백한 동작 변경이다.
- 따라서 1단계의 목표는 "쓰기 시점 변경"이 아니라 **"쓰기 주체를 인터페이스 뒤로 옮기기"**다.

- **검증:** 게임을 돌려 이전과 동일하게 저장·로드되고, **가시 동작과 내구성이 모두 현행과 같으면** 완료.

여기서 정할 세부 결정 세 개.

```text
flush 경계     원격 백엔드가 강제 flush 할 시점 (화면 전환 / 레이드 경계 / 종료)
               로컬은 해당 없음 (즉시)
dirty 단위     전체 덩어리 vs server_owned·client_owned 컬럼별
실패 전달      백엔드 실패를 호출자와 UI 에 어떻게 올릴지
               로컬은 사실상 항상 성공이라 이 경로는 2a 에서 처음 실제로 쓰인다
```

로컬 즉시 저장의 성능 비용(슬롯 하나 옮길 때마다 전체 `SaveGame` 직렬화)은 별개 최적화 주제이며, 전환의 전제가 아니다.

### 2a단계 — 원격 저장소 왕복

```text
- Build.cs 에 "HTTP" 추가 (Json 은 이미 있음)
- users / identities / profiles 스키마 생성 (위 결정대로, profile_revision 포함)
- 전송 DTO + schema_version
- 인증은 개발용 provider, Steam 없이 (아래 주의)
- FJsonObjectConverter 로 DTO ↔ JSON
- 타이틀에 "접속 중" 게이트, 저장 실패 표시 UX
- 토큰 만료·갱신 경로 (넣지 않으면 "장시간 플레이 후 저장 실패"로 나중에 터진다)
```

**개발용 인증은 "디바이스 ID"로는 부족하다.** 디바이스 ID는 기기마다 다르므로 다른 PC에서 같은 신원으로 로그인할 수단이 없다. 즉 아래 검증 자체를 수행할 수 없다. 최소한 다음 중 하나가 필요하다.

```text
개발 계정 코드     사람이 입력하는 짧은 코드 → 같은 user_id 로 해석
테스트 자격증명    팀 공용 계정 몇 개를 미리 만들어 두고 선택
토큰 가져오기      A 기기에서 발급된 토큰을 B 기기에 수동 입력
```

`identities` 테이블 구조를 그대로 쓰면 `provider='dev'` + `provider_id=<코드>`로 해결된다. 어느 방식이든 **"신원을 기기와 분리"**하는 게 요점이고, 그래야 2b의 Steam 교체가 같은 자리 갈아끼우기로 끝난다.

**검증:** A PC에서 아이템을 얻고, B PC에서 **같은 개발 계정 코드로** 로그인해 그 아이템이 보이면 성공. 이어서 A PC를 다시 열어 `profile_revision` 충돌이 감지되는지도 확인한다.

여기까지는 클라가 자기 행을 직접 쓰므로 **여전히 치트 가능하다.** 얻는 것은 조작 방지가 아니라 PC 독립성과 다음 단계의 토대다.

### 2b단계 — Steam Auth로 신원 교체

**현재 프로젝트에 Steam 설정은 전무하다.** `.uproject`에 OnlineSubsystemSteam이 없고, `Config/`에 Steam 항목이 없고, `steam_appid.txt`도 없다.

Steam Auth는 최종적으로 **맞는 선택**이다. 미루는 이유는 기술 판단이 아니라 조달이 임계 경로이기 때문이다.

왜 필요한가:

- **밴 회피 비용.** 익명/디바이스 인증은 밴당하면 새 ID를 공짜로 만든다. 아이템 복제 어뷰저를 잡아도 곧 돌아온다. Steam 계정 밴은 게임을 다시 사야 한다.
- **소유권 확인** (`CheckAppOwnership`으로 정품 여부를 서버가 확인).
- **비밀번호를 우리가 저장하지 않는다.** 자체 계정 시스템은 해싱·이메일 인증·복구 흐름·유출 책임을 전부 우리 것으로 만든다.
- 무료이고 유저 입장에선 로그인 화면이 없다.

작업 내용:

```text
- Steamworks 파트너 계정 + AppID 확보 (선행 조달, 앱 등록비 발생)
- OnlineSubsystemSteam 플러그인 활성화
- 클라: GetAuthTicketForWebApi 로 티켓 획득
- 백엔드: Steam Web API 로 티켓 검증 → identities 에 provider='steam' 행
- 개발용 provider 는 그대로 유지
```

틀리기 쉬운 지점:

- **`GetAuthTicketForWebApi`를 쓴다.** 구형 `GetAuthSessionTicket`은 게임서버↔Steam 검증용 설계라 웹 백엔드에 쓰면 티켓을 다른 서비스에 재사용당할 여지가 있다. 전용 API는 티켓을 우리 서비스에 묶는다.
- **Publisher Web API 키는 백엔드에만.** 클라나 데디서버 패키징에 들어가면 안 된다.
- 티켓은 **한 번만** 교환해 우리 세션 토큰으로 바꾸고, 이후 갱신은 우리 토큰으로 한다. Steam 티켓을 계속 들고 다니지 않는다.

2a에서 만든 세션 토큰·갱신·게이트 UI·저장 경로가 전부 재사용된다. 바뀌는 것은 "신원을 어디서 받아오나" 한 곳뿐이다.

### 3단계 — 경제 서버 권위

DB 쪽 비중은 오히려 작고, 무거운 것은 게임 구조 변경과 명령 API 설계다.

| 요소 | 난이도 |
|---|---|
| RLS 정책 + 컬럼 권한 + 전용 서버 역할 | 낮음 |
| 서버 크리덴셜 분리 (클라 패키징 금지) | 낮지만 실수하면 치명적 |
| **로비 경제 명령 API** (제작·상점·판매) | **높음** |
| 배치 전송 경로 (`rearrange` + 집합 보존 검증) | 중 |
| 레이드 결과 ACK 흐름 재설계 + 멱등 커밋 | 높음 |
| 데디케이티드 서버 전환 | 높음 (별개 작업 — [DedicatedServerBuildout.md](DedicatedServerBuildout.md)) |

#### 로비 경제 권위를 어디에 둘 것인가

서버 권위를 한다는 가정에서, "클라 로컬 vs 서버"는 잘못된 이지선다다 — **여기서 말하는 "서버"가 UE 데디서버일 필요가 없기 때문이다.** 선택지는 셋이다.

| | 경제 권위 | 프로세스 | 비용 곡선 |
|---|---|---|---|
| A. 현행 = **출시 방침** | 클라이언트 | 없음 | 0 |
| **B. 백엔드 서비스** (이 문서가 다루는 안) | 서버 | HTTP 함수/RPC | 요청당 |
| C. UE 데디 로비 | 서버 | UE 서버 상시 인스턴스 | **동시 접속자당 시간** |

**B와 C는 조작 방지 관점에서 완전히 동등하다.** 둘 다 제작·상점·창고가 서버 검증을 거친다. 차이는 그것을 무엇으로 돌리느냐뿐이다. 그래서 서버 권위를 한다면 B를 고른다.

C를 배제하는 이유:

```text
로비가 메뉴 화면이다   ALSLobbyGameMode 는 DefaultPawnClass = nullptr 로 폰 스폰을 막고
                       BeginPlay 에서 곧바로 WBP 를 띄우고 UI 입력 모드로 전환한다
                       캐릭터가 돌아다니는 3D 공간이 아니다 (기획 확정)

비용 곡선이 나쁘다     레이드 서버는 동시 "매치" 수에 비례하지만
                       로비 서버는 동시 "접속자" 수에 비례한다
                       플레이어는 레이드보다 로비에 오래 머문다

낭비가 크다            틱·리플리케이션·액터 생명주기를 전부 지불하고
                       실제로 하는 일은 DB 트랜잭션 하나다

가용성                 로비 서버가 죽으면 인벤토리조차 볼 수 없다
```

C가 정당해지는 유일한 조건은 3인이 서로를 보는 **공유 3D 허브**를 원할 때인데, 그건 게임 디자인 결정이지 조작 방지 결정이 아니다. 현재 기획은 로비를 UI로만 유지하기로 확정했다.

#### 쓰기 경로를 둘로 나눈다 (배치 / 명령)

모든 로비 조작을 서버 왕복으로 만들면 안 된다. **가치가 변하는 조작만 개별 검증이 필요하다.**

```text
가치 보존   정렬, 슬롯 이동, 인벤↔창고↔금고 이동, 장착/해제, 퀵슬롯, 버리기
            아이템 집합이 그대로다 → 반복해도 이득이 0 → 개별 검증 불필요
가치 변동   제작, 구매, 판매, 레이드 결과 커밋
            없던 것이 생기거나 재화가 바뀐다 → 개별 검증 필수
```

따라서 `server_owned`에 쓰기 경로가 **둘** 필요하다.

```text
rearrange(new_layout)                배치 제안. 인메모리로 즉시 반영하고
                                     경계에서 1회 전송 (패널 닫기 / 화면 전환 / 레이드 입장)
                                     서버 검증 = 아이템 다중집합 보존 + 슬롯 용량·타입·잠금 규칙

craft(recipe_id, count)              재료·골드 검증 후 원자적 차감/지급
purchase(item_id, count)             재고·골드 검증
sell(...) / raid_commit(raid_id,...) 개별 검증
```

**`rearrange`가 안전한 이유:** 서버가 가진 현재 상태의 아이템 다중집합과 클라가 보낸 배열의 다중집합이 일치할 때만 수락한다. "재배치"로 위장해 아이템을 끼워넣으면 집합이 달라져 걸린다. 정렬 후 비교라 검증 비용도 싸다. 용량 검사가 함께 필요한 이유는 금고(SafeStash)처럼 레이드 사망 시 생존하는 영역이 있어 칸 수를 클라가 우기지 못하게 막아야 하기 때문이다.

이 구분 덕분에 **정렬·드래그앤드롭·Shift-click 코드는 지금의 동기 인메모리 흐름 그대로 남는다.** 드래그 50번의 전송이 1번이 된다. 실제 왕복이 생기는 것은 제작·구매뿐이고, 이건 원래 확인 순간이 있는 조작이라 자연스럽다. 그래도 거슬리면 낙관적 UI(먼저 반영 → 거절 시 롤백)로 체감을 없앨 수 있다.

> 이 분할은 위 `3단계는 쪼갤 수 없다`를 약화시키지 않는다. `rearrange`는 집합 보존을 강제하므로 위조 경로가 되지 못하고, 가치를 만드는 경로는 전부 `command`로 남기 때문이다.

`ULSSaveSubsystem::TryCraft`가 이미 "양쪽 다 불가능하면 저장 상태를 전혀 바꾸지 않는다"로 원자성을 손으로 구현해두었다. 이 규칙을 SQL 트랜잭션으로 옮기면 보장이 엔진 쪽으로 내려간다. 검증 규칙 자체는 이미 C++에 있으므로 **옮기는 작업이지 새로 만드는 작업은 아니다.** 다만 DataTable 값을 서버가 읽을 수 있어야 하므로, 레시피·가격 테이블을 DB에도 넣거나 서버가 같은 데이터를 참조할 경로가 필요하다.

여기서 jsonb → 관계형 정규화가 필요해질 수 있다.

#### 레이드 결과 커밋

ACK 흐름의 **의미가 바뀐다.** 현재는 서버가 결과 payload를 보내고 클라가 로컬에 저장한 뒤 ACK한다([ItemSaveNetworkStructure.md](ItemSaveNetworkStructure.md)의 `레이드 종료 흐름` 참조). 전환 후 순서는 이렇게 되어야 저장이 유실되지 않는다.

```text
서버가 DB 에 결과 write 성공 (raid_id 멱등 키 포함)
→ 클라에 "다시 읽어라" 통지
→ 클라가 read 완료 ACK
→ ResultLevel 이동
```

핵심은 클라가 통지를 못 받아도 **서버 쪽 저장은 이미 확정**이라는 점이다. 그리고 write가 타임아웃되어 서버가 재시도할 때 `raid_id`가 없으면 보상이 중복 지급된다(위 `동시성과 멱등성` 참조).

## 순서의 근거

```text
1  어떤 백엔드를 고르든 필요하고, 되돌리기 쉽고, 지금 당장 착수 가능
2a 2b 의 대부분을 미리 만든다 (신원만 빠진 완성 경로)
2b 조달(AppID)이 임계 경로
3  데디케이티드 전환 + 경제 명령 API 전체가 묶여 있어 압도적으로 무겁다
   앞 단계가 서 있어야 안전하게 검증된다
```

AppID를 이미 확보할 수 있으면 2a를 건너뛰고 2b로 직행해도 설계는 동일하다.

3단계는 앞의 셋을 합친 것보다 크다. **학습 목적이라면 1 → 2a → 2b까지가 현실적인 목표**이고, 3단계는 [DedicatedServerBuildout.md](DedicatedServerBuildout.md)와 함께 별도 프로젝트로 다루는 편이 낫다.


## 미결정 사항

```text
- 1단계 세부 3개 (flush 경계 / dirty 단위 / 실패 전달)
- 학습을 몇 단계까지 진행할지 (1 / 2a / 2b, 3단계는 별도 판단)
- 관리형 서비스 구체 선정 (Supabase 등) — 2a 착수 시
- 개발용 provider 방식 확정 (계정 코드 / 공용 자격증명 / 토큰 가져오기)
- 거래 원장 테이블의 기록 시점과 보존 기간 — 3단계 이후에만 의미
- 3단계 시 DataTable(레시피 · 가격)을 서버가 어떻게 참조할지
```

**Steamworks AppID는 학습 여부와 무관하게 출시 임계 경로에 있다.** Steam Cloud 자체가 AppID와 파트너 사이트 설정을 요구하기 때문이다. 현재 프로젝트에는 Steam 설정이 전무하다(위 2b단계 참조).

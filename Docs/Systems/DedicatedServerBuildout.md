# 멀티플레이 · 데디케이티드 서버 구축 계획

## 이 문서의 범위

3인 MO 멀티플레이를 실제로 돌리기까지 필요한 **엔진·빌드·운영 측 작업**의 단일 출처다. 빌드 타깃, 패키징, 서버 시작 맵, 플레이어 접속·이탈, 전역 상태 정리, 매치 할당, 프로세스 수명, 시크릿 주입, 헤드리스 검증을 다룬다.

**접속 경로는 셋이다** (근거는 아래 `E2 결정`).

```text
IP 직접 / 친구 방        리슨 (호스트 클라)   친구를 신뢰        우리 비용 0
커뮤니티 서버 목록        유저 운영 데디        운영자를 선택적 신뢰  방 목록 서비스만
공개 매칭                우리 운영 데디        신뢰 불필요        매치 시간당
```

**레이드는 개별 탈출 + 관전자 방식이다.** 탈출한 플레이어는 관전으로 남고 나머지는 계속 진행한다.

작업 항목 중 **C·D·E는 세 경로 공통(멀티플레이 작업)**이고, **A·B·F·G1만 데디 전용**이다. 문서 제목이 데디를 달고 있지만 내용의 다수는 리슨에도 그대로 필요하다.

인접 문서와의 경계:

>
> 둘은 **양립한다.** 레이드 중에는 서버가 권위를 갖고, 영속 저장은 각 클라이언트 로컬 파일에 남는 구조가 현재 설계다.

**현재 구현 상태: 미착수.** 서버 빌드 타깃이 없어 데디케이티드 빌드가 불가능하고, 플레이어 접속·이탈 처리와 전역 상태 정리도 되어 있지 않아 리슨 3인도 아직 성립하지 않는다.

## 현재 상태 (실측)

### 있는 것

```text
GameMode 4종        LSTitleGameMode / LSLobbyGameMode / LSFarmingGameMode / LSResultGameMode
                    (+ 공통 베이스 LSGameModeBase)
서버 권위 레이드    ULSRaidInventoryComponent 기반 루팅·사용·드랍·사망·탈출 확정
입장/결과 ACK       제출 ACK, 결과 저장 ACK, 각각 타임아웃 처리까지 구현됨
데디 대비 분기      NM_DedicatedServer 분기 12곳
                    렌더/위젯/프리뷰 계열이 서버에서 스킵되도록 이미 처리됨
```

레이드 자체의 서버 권위 로직은 상당 부분 서 있다. 빠진 것은 **그 로직을 담을 서버 프로세스**다.

### 없는 것

```text
서버 빌드 타깃      Source/ 에 LostSignal.Target.cs (TargetType.Game) 와
                    LostSignalEditor.Target.cs 만 존재
                    → LostSignalServer.Target.cs 부재 = 데디 빌드 불가

플레이어 접속 처리  PostLogin / Logout / GetNumPlayers 사용처 0곳
                    누가 언제 들어오고 나갔는지 다루는 코드가 없다

SeamlessTravel      bUseSeamlessTravel 사용처 0곳
                    ServerTravel 시 연결이 끊겼다 다시 붙는다

세션 / 매칭         CreateSession / FindSession / JoinSession / OnlineSubsystem 0곳
                    Build.cs 의 OnlineSubsystem 은 주석 처리된 템플릿 기본값

서버 시작 맵        Config/DefaultEngine.ini 에 ServerDefaultMap 없음
                    GameDefaultMap 은 L_Title (서버가 타이틀을 띄울 이유가 없다)
```

### 주의가 필요한 기존 구조

**① 전역 세션 상태의 순서 기반 큐**

`ALSLobbyGameMode::StartRaid`가 `ServerTravel` 직전에 각 플레이어 데이터를 `ULSSessionSubsystem`에 순서대로 넣는다.

```text
SessionSub->EnqueuePendingRaidEntry(PlayerLoadout, PlayerSafeItems, PlayerEquipment);
// 주석: "ServerTravel 이후 각 PC가 자신의 데이터를 꺼낼 수 있도록 순서대로 큐에 저장"
```

`ULSSessionSubsystem`은 GameInstance 서브시스템이라 **데디서버에는 전 플레이어가 공유하는 인스턴스가 하나뿐이다.** 순서에 의존해 자기 데이터를 꺼내는 방식은 접속 순서·재접속·중도 이탈에 취약하다. [ItemSaveNetworkStructure.md](ItemSaveNetworkStructure.md)에도 "이 보호가 없으면 ServerTravel 이후 모든 플레이어 인벤토리가 첫 번째 플레이어 데이터로 덮일 수 있다"고 기록된 알려진 취약점이다.

같은 함수에 `bHasLegacySessionLoadout` / `MirrorRaidSessionState`처럼 단일 플레이어 시절의 전역 미러링 경로도 남아 있다. 3인 환경에서 전역 미러는 정의상 누군가에겐 틀린 값이다.

→ **PlayerState 또는 안정적인 플레이어 키 기반으로 교체해야 한다.** 데디 전환의 선행 정리 항목.

**② 글로벌 기본 GameMode가 블루프린트**

```text
GlobalDefaultGameMode=/Game/TopDown/Blueprints/BP_TopDownGameMode
```

C++ 전용 프로젝트인데 템플릿 잔재인 BP GameMode가 전역 기본값이다. 서버가 맵별 GameMode 지정 없이 뜨면 이게 걸린다. 에셋 위치(`/Game/TopDown/`)도 `Content/LostSignal/` 규칙 밖이다.

## 작업 항목

### A. 빌드 / 패키징

```text
A1  LostSignalServer.Target.cs 추가 (TargetType.Server)
    ExtraModuleNames 는 Game 타깃과 동일하게 맞추되 서버 불필요 모듈 검토
A2  서버 타깃 컴파일 통과
    에디터 전용 / 렌더 전용 코드가 서버 타깃에서 링크되는지 확인
    LostSignalVisionShaders 등 렌더 모듈의 서버 빌드 가부 판단
A3  데디케이티드 서버 패키징 커맨드 확립 (기존 클라 패키징과 별도)
A4  서버 빌드 산출물에 클라 전용 에셋이 빠지는지 / 용량 확인
```

A2가 실질적 관문이다. `NM_DedicatedServer` 런타임 분기는 12곳 있지만, 그건 **실행 시 스킵**이지 **컴파일 시 제외**가 아니다. 서버 타깃에서 처음 빌드하면 렌더/UMG 의존이 드러난다.

### B. 서버 부팅 / 맵

```text
B1  ServerDefaultMap 지정 (레이드 맵 또는 대기용 빈 맵)
B2  GlobalDefaultGameMode 를 C++ 클래스로 교체 (BP_TopDownGameMode 제거)
B3  맵별 GameMode 매핑 확인 (GameModeMapPrefixes 또는 월드 세팅)
B4  서버 커맨드라인 인자 정리 (포트, 로그, 맵)
```

### C. 플레이어 접속 / 이탈

현재 완전히 비어 있는 영역이다.

```text
C1  PostLogin  - 플레이어 입장 시 PlayerState 초기화, 접속 인원 카운트
C2  ✅ 결정됨 - 중도 이탈 / 호스트 이탈 처리 (아래 참조)
C3  재접속 정책 - 허용할지, 허용하면 세션 상태를 어떻게 복구할지
C4  최소/최대 인원 판정 - 3인 MO 기준 시작 조건
C5  입장 payload 정합성 검증 - 공개 매칭의 전제 조건 (아래 참조)
C6  개별 탈출 - EndRaid 를 플레이어별 결과 확정 경로로 개조 (아래 참조)
C7  관전자 - 탈출/사망 후 관전 폰·카메라·UI
            탈출자에게 로비 UI 오버레이를 줄지 함께 결정
            (ALSLobbyGameMode 는 DefaultPawnClass=nullptr 인 순수 위젯이라 얹기 쉽다)
```

#### 탈출 모델: 개별 탈출 + 관전자

```text
플레이어가 탈출존 도달  → 그 플레이어만 결과 확정 (뱅킹)
                        → 관전 상태로 전환, 나머지는 레이드 계속
전원 탈출 / 사망        → 세션 종료
```

**현재 코드는 개별 탈출을 지원하지 않는다.** `ALSFarmingGameMode::OnExtraction`이 곧바로 `EndRaid(Extracted)`를 부르고, `EndRaid`가 모든 PlayerController를 순회해 한 번에 끝낸다. 즉 지금은 한 명이 탈출하면 전원 종료다. **플레이어별 결과 확정 경로로의 개조가 이 방향의 최대 작업**이며, 세 접속 경로 모두의 공통 선행 작업이다.

`BuildRaidResultForPlayer`가 이미 플레이어 단위로 호출되고 Result에 따라 영역별 저장 여부를 결정하므로, `EndRaid`가 **플레이어별로 다른 Result를 넘길 수 있게** 하는 것이 개조의 축이다.

#### C2 결정: 호스트 이탈 시 생존자의 소지품을 확정한다

```text
호스트 이탈  → 남은 플레이어  현재 소지품을 그대로 확정 (잃지 않음)
              → 호스트        Quit 처리 (자기 전리품 소실, 장비는 보존)
비호스트 이탈 → 이탈한 본인만 Quit 처리, 나머지 레이드는 계속
```

> **이 규칙은 개별 탈출의 전제 조건이다. 선택 사항이 아니다.**

개별 탈출과 관전을 넣으면서 이 규칙이 없으면 **비용 0의 그리핑 도구**가 만들어진다.

```text
1. 호스트가 먼저 탈출 → 자기 전리품 뱅킹 완료
2. 관전 상태 = 더 잃을 것이 없음
3. 게임 종료 → 서버 소멸 → 남은 인원 전리품 소실
4. 호스트 손실 0
```

악의가 없어도 벌어진다. 볼일이 끝나 창을 닫는 것만으로 남의 판이 날아간다. 위 규칙을 넣으면 나가봐야 남이 잃는 게 없으므로 그리핑 가치가 0이 되고, 호스트는 자기 전리품을 잃으므로 고의 이탈 유인도 없다.

친구끼리 담합(번갈아 호스트를 맡고 일부러 나가 무위험 확정)은 가능하지만, 그 경로는 친구 한정이고 로컬 세이브라 파일을 직접 고치는 편이 더 쉽다. 실질 위험이 없다.

구현은 확장에 가깝다 — 기존 Quit 복구 경로(`ActiveRaidLoadout` 기반, 장비는 "저장 생략"이 곧 복구)는 [ItemSaveNetworkStructure.md](ItemSaveNetworkStructure.md)가 단일 출처이고, 여기에 "생존자 소지품 확정" 케이스가 추가된다.

#### 호스트 마이그레이션은 만들지 않는다

호스트가 나갈 때 다른 클라이언트로 권위를 넘기는 구조는 채택하지 않는다.

```text
UE 에 내장 없음
ULSRaidInventoryComponent 는 리플리케이션이 전혀 없다
  → 서버 프로세스 메모리에만 존재하고 클라에는 RPC 로 단방향 미러만 보낸다
  → 호스트가 죽으면 전원의 권위 인벤토리가 열화가 아니라 소멸한다
그 외에도 몬스터 HP · StateTree · 어그로, GAS 효과 · 쿨타임,
룻박스 내용물, 월드 드랍, 신호 게이지 타이머가 모두 서버 전용 상태다
```

마이그레이션을 하려면 전원의 인벤토리를 전원에게 복제하거나(대역폭 + 남의 인벤토리를 클라가 쥠) 섀도 호스트에 주기적 전체 스냅샷을 보내야 한다. 그리고 익스트랙션에서 **인벤토리 상태가 조금이라도 어긋나면 판이 끝나는 것보다 나쁘다.**

**어떤 미래 조합에서도 최선이 되지 않는다.** 위 C2 규칙이 실제 피해(전리품 손실)를 이미 없애고, 데디 경로에는 호스트가 아예 없다.

#### 미해결: 접속 종료로 사망 회피 (combat logging)

현재 Quit은 장비를 보존하고 Dead는 소멸시키므로, **죽기 직전 게임을 종료하면 장비를 지킬 수 있다.** 호스팅 모델·탈출 모델과 무관하게 이미 존재하는 문제이지만, 개별 탈출과 관전을 넣으면 더 눈에 띈다.

통상적인 해법은 "접속 종료 후에도 캐릭터가 N초간 월드에 남는다"이다. 별도 판단이 필요한 항목으로 남긴다.

#### C5: 입장 payload 정합성 검증

**공개 매칭을 여는 순간 필수가 된다.** 현재는 [ItemSaveNetworkStructure.md](ItemSaveNetworkStructure.md)에 "최초 제출 데이터는 DB 서버가 없으므로 어쩔 수 없이 신뢰한다"고 적힌 대로 검증이 전혀 없다. 로컬 세이브를 유지하는 이상 클라가 제출하는 로드아웃은 위조 가능하다.

```text
- 존재하지 않는 아이템 Row 거부
- 슬롯 용량 · 타입 · 잠금 규칙 위반 거부
- 등급 · 수량 상한 초과 거부
```

완전한 위조 차단은 아니다. **합법적으로 도달 가능한 최대치까지는 여전히 위조 가능**하며, 그 이상을 막으려면 백엔드 경제 권위([SaveBackendMigration.md](SaveBackendMigration.md) 3단계)가 필요하다. 다만 데디서버가 이미 하는 일에 검사 몇 개를 붙이는 수준이라 비용 대비 효과가 크다.

PvE 코옵이라 위조 로드아웃의 피해는 "판이 시시해진다" 정도이고 남의 재산을 파괴하지는 않는다. 남용이 실제 문제가 되면 그때 3단계로 올린다.

### D. 여행 / 세션 상태

```text
D1  bUseSeamlessTravel 도입 여부 판단
    끄면 ServerTravel 마다 연결이 끊겨 재접속 처리가 필요하다
D2  EnqueuePendingRaidEntry 순서 기반 큐를 플레이어 키 기반으로 교체
D3  MirrorRaidSessionState / bHasLegacySessionLoadout 등 단일 플레이어 전역 경로 제거
D4  ULSSessionSubsystem 의 남은 전역 상태 정리 (데디에서는 인스턴스가 하나뿐)
```

D2·D3는 **리슨·데디 양쪽 모두의 선행 조건**이다. "데디를 안 하니 건너뛴다"가 성립하지 않는다 — 순서 기반 큐와 전역 미러링은 리슨 3인에서도 똑같이 인벤토리를 섞는다. C·D·E는 데디 작업이 아니라 **멀티플레이 작업**이고, 데디 전용은 A·B·F·G1뿐이다.

### E. 매치 할당 / 접속

```text
E1  ✅ 결정됨 - 매칭/방 목록은 발견 계층, 접속 경로는 셋 (아래 참조)
E2  ✅ 결정됨 - 공개 = 데디 / IP 직접 = 리슨, 로비는 클라 로컬 (아래 참조)
E3  레이드 종료 후 클라이언트 복귀 경로 (서버 유지 / 해산 후 로컬 복귀)
E4  OnlineSubsystem(Steam) 도입 여부 — 세션 검색·NAT 통과에 필요할 수 있음
```

#### E1 결정: 매칭은 발견 계층이다

**매칭 서비스와 전송을 분리한다.** 매칭은 "어느 주소로 갈지"만 알려주고, 접속 자체는 어느 경로든 같은 지점으로 수렴한다.

```text
공개 매칭     우리 매칭 서비스가 서버 주소를 돌려준다
IP 직접 입력  플레이어가 주소를 직접 넣는다
              ↓
        양쪽 모두 같은 접속 경로 (ClientTravel)
```

이 분리의 효과는 **우리 매칭 서비스가 죽어도, 나중에 운영을 접어도 게임이 계속 돈다**는 것이다. IP 직접 연결만으로 친구끼리 플레이가 성립해야 한다.

##### 가용성 요구사항: 공개 매칭 실패는 공개 매칭만 막는다

데디/매칭이 불가능한 상황은 넷이고, **전부 같은 결과여야 한다** — 공개 매칭 진입점만 비활성, 나머지는 전부 정상.

```text
매칭 서비스 장애
가용 서버 인스턴스 없음 (전부 사용 중)
데디 빌드가 아직 없음 (개발 기간)
나중에 서비스 운영 중단
        ↓
공개 매칭 버튼만 비활성 · 안내 표시
로비 진입 · 인벤토리 · 제작 · 창고 · IP 직접 연결은 정상
```

이를 지키기 위한 구현 제약:

```text
부팅 경로에 매칭 의존 금지   타이틀 · 로비 진입이 매칭 서비스 응답을 기다리면 안 된다
                             가용성 조회는 공개 매칭 화면에 들어갈 때만 (지연 조회)
                             영구 저장이 로컬이라 부팅에 네트워크 의존이 애초에 없다 — 그 이점을 깨지 말 것

타임아웃 · 폴백 UX           매칭 요청 실패 시 "공개 매칭을 이용할 수 없습니다.
                             IP 직접 연결로 플레이할 수 있습니다" 수준의 안내

기능 플래그                  데디 빌드가 없는 개발 기간에도 공개 매칭 진입점을 숨기거나
                             비활성으로 둘 수 있어야 한다
                             그래야 아래 D-3 시점의 "출시 가능한 상태"가 실제로 성립한다
```

**부팅 경로 제약이 가장 중요하다.** 여기가 깨지면 매칭 서비스 장애가 곧 게임 실행 불가가 되어, 이 절의 목적이 통째로 무의미해진다.

#### E2 결정: 신뢰 수준에 서버 모델을 맞춘다 (3계층)

| 경로 | 서버 | 레이드 권위 | 신뢰 모델 | 우리 비용 |
|---|---|---|---|---|
| **IP 직접 / 친구 방** | 리슨 (호스트 클라) | 호스트 | 친구를 신뢰 | 0 |
| **커뮤니티 서버 목록** | 유저 운영 데디 | 서버 | 운영자를 **선택적** 신뢰 | 방 목록 서비스만 |
| **공개 매칭** | 우리 운영 데디 | 서버 | 신뢰 불필요 | 매치 시간당 |

공통으로 **로비 UI·로비 경제는 클라이언트 로컬**이고 **영구 저장은 로컬 `SaveGame` + Steam Cloud**다. 로비를 위해 서버 프로세스를 띄우지 않는다.

##### 유저 운영 데디는 치트 방지를 주지 않는다

혼동하기 쉬운 지점이라 명시한다. **유저가 운영하는 데디서버는 신뢰 관점에서 리슨과 다르지 않다** — 운영자가 서버 바이너리를 고치거나 변조된 빌드를 돌리면 그 사람이 곧 권위다.

```text
             호스트 이탈 내성   레이턴시 공정성   치트 방지
리슨              ✗               ✗              ✗
유저 운영 데디     ✅              ✅             ✗
우리 운영 데디     ✅              ✅             ✅
```

즉 유저 운영 데디는 **가용성·공정성 이점만** 준다. 그래서 이것으로 공개 매칭을 대신할 수 없다. 다만 **자동 배정되는 "매칭"이 아니라 골라서 들어가는 "서버 목록"**이면 신뢰가 opt-in이 되어 정당해진다(Minecraft·Valheim 커뮤니티 서버의 사회적 계약).

##### 공개 매칭에 리슨을 쓰면 안 되는 이유

```text
치트가 필요한 문제    호스트가 곧 서버이므로 루팅 롤·데미지·스폰·탈출을 전부 확정한다
                      익스트랙션에서 사망은 장비 손실이므로
                      악의적 호스트가 모르는 사람의 인벤토리를 실제로 파괴할 수 있다
치트가 불필요한 문제  호스트가 그냥 나가면 남의 판이 끝난다   ← 훨씬 흔하다
```

두 번째가 결정적이다. 모르는 사람끼리는 호스트 이탈이 일상적으로 발생하므로(화나서, 크래시, 그냥 종료) 치터가 없어도 빈도만으로 무너진다. C2 규칙이 전리품 손실은 막아주지만 **판이 중단되는 것 자체**는 막지 못한다.

##### (a) 우리 운영 vs (b) 유저 운영 — 순서

**둘은 같은 서버 타깃을 쓴다.** 차이는 누가 프로세스를 실행하느냐와 앞단 서비스가 방 목록이냐 매치 배정이냐뿐이다.

```text
(b) 까지   서버 타깃 + 방 목록 서비스              운영 부담 0
(a) 추가   같은 바이너리를 우리가 돌리고
           배정 로직과 인스턴스 풀을 얹는다         운영 부담 발생
```

따라서 **(b)를 먼저 하고 (a)를 나중에 얹는다.** (b)는 (a)로 가는 길을 막지 않고 오히려 선행 작업이며, 운영 비용이 붙는 시점을 늦춘다.

세 넷모드를 지원하는 비용이 붙지만, 코드에 이미 `NM_DedicatedServer` 분기가 12곳 있고 C·D 항목은 전 경로 공통이라 데디 추가분은 A·B·F·G1에 한정된다.

이 구성은 [ItemSaveNetworkStructure.md](ItemSaveNetworkStructure.md)에 이미 기록된 현재 신뢰 경계와 정확히 일치한다 — 레이드 입장 시 제출 데이터는 신뢰하고, 레이드 중에는 서버 상태만 신뢰하며, 결과는 서버가 계산해 클라 로컬 세이브에 반영한다. 즉 **E2는 새 아키텍처를 도입하는 결정이 아니라 현재 구조를 유지하는 결정**이고, 이 문서가 추가하는 것은 그 레이드 권위를 담을 실제 서버 프로세스뿐이다.

로비가 메뉴 화면이라는 점도 이를 뒷받침한다. `ALSLobbyGameMode`는 `DefaultPawnClass = nullptr`로 폰 스폰을 막고 `BeginPlay`에서 곧바로 WBP를 띄운 뒤 UI 입력 모드로 전환한다. 캐릭터가 돌아다니는 3D 공간이 아니며, 기획도 로비를 UI로만 유지하기로 확정했다. **공유 3D 로비 허브는 범위 밖이다.**

##### 백엔드 경제 권위는 이 문서의 결정이 아니다

로비 경제를 HTTP 백엔드가 검증·저장하는 구성은 **출시 방침과 양립하지 않는다.** 출시 방침은 로컬 `SaveGame`을 영구 저장 원본으로 두고 백엔드 경제 권위를 두지 않기 때문이다. 그 구성은 [SaveBackendMigration.md](SaveBackendMigration.md)의 **학습용 3단계**로만 존재하며, 채택하려면 로컬 세이브 출시 방침 자체를 폐기해야 한다.

정리하면 경계는 이렇다.

```text
이 문서 (실제 로드맵)          레이드를 돌릴 데디서버 프로세스를 만든다
                               로비 경제는 건드리지 않는다

SaveBackendMigration (학습용)  로비 경제까지 서버 권위로 옮기는 연습
                               그 안에서 "UE 데디 로비 vs 백엔드 서비스" 비교를 다룬다
```

나중에 공유 허브나 백엔드 경제 권위를 실제로 채택하게 되면, 그건 이 절을 고치는 별도 결정이다.

### F. 운영

```text
F1  프로세스 수명 - 레이드 종료 후 서버를 내릴지 재사용할지, 유휴 타임아웃
F2  런타임 시크릿 주입 - 커맨드라인/환경변수/설정 파일 중 무엇으로
                        클라 패키징에 절대 포함되지 않을 것
F3  로그 수집 - LogLS 카테고리를 서버에서 어떻게 남기고 회수할지
F4  크래시 처리 - 레이드 중 서버 크래시 시 참가자 결과 정책
```

### G. 검증

```text
G1  헤드리스 실행 확인 (렌더 없이 뜨는지)
G2  서버 1 + 클라 2~3 로컬 접속 테스트
G3  레이드 입장 payload 가 플레이어별로 안 섞이는지  ← D2/D3 회귀 테스트
G4  중도 이탈 / 호스트 이탈 시나리오
    호스트 이탈 시 생존자가 소지품을 확정받는지, 호스트만 Quit 처리되는지
    "먼저 탈출 → 관전 → 종료" 로 남을 그리핑할 수 없는지
G7  개별 탈출 / 관전 시나리오
    한 명 탈출 후 나머지 레이드가 계속되는지, 결과가 섞이지 않는지
G5  결과 저장 ACK 타임아웃 경로
G6  ★ 매칭 서비스를 끈 상태에서 게임 완주
    타이틀 · 로비 · 인벤토리 · 제작이 정상이고
    IP 직접 연결로 레이드까지 완주되는지
    공개 매칭 진입점만 비활성인지
```

**G6은 회귀 테스트로 상시 유지한다.** 누군가 부팅 경로에 매칭 의존을 끼워 넣는 순간 이 테스트가 깨져야 한다. 위 `가용성 요구사항`을 코드로 지키는 유일한 수단이다.

G3은 기존 테스트 체크리스트([ItemSaveNetworkStructure.md](ItemSaveNetworkStructure.md)의 `2인 테스트 준비 후`)와 겹치므로 그쪽을 재사용한다.

## 단계 제안

**공통 기반 → 리슨 → 유저 운영 데디 → 우리 운영 데디** 순서다. 운영 비용이 붙는 시점을 가장 뒤로 민다.

| 단계 | 범위 | 끝나면 | 경로 |
|---|---|---|---|
| **D-1** | D2~D4 (전역 상태 정리) | 3인 데이터가 안 섞이는 구조 | 공통 |
| **D-2** | C1~C4 (접속/이탈) + C2 이탈 규칙 | 입장·이탈이 정의된 동작을 한다 | 공통 |
| **D-3** | C6~C7 (개별 탈출 + 관전자) | 각자 원할 때 빠지고 관전한다 | 공통 |
| **D-4** | E1·E3 (IP 직접 연결) | **친구끼리 리슨으로 레이드 완주** | 리슨 |
| **D-5** | A + B (서버 타깃·부팅) + 방 목록 | 유저가 서버를 띄우고 목록에서 찾는다 | 유저 데디 |
| **D-6** | C5 + 매치 배정 + F | 공개 매칭으로 레이드 완주 | 우리 데디 |
| **D-7** | G | 검증 | 전체 |

**D-1을 맨 앞에 두는 이유:** 전역 상태 정리를 미루면 접속 처리를 붙이는 순간 인벤토리 혼선이 접속 버그처럼 보여 원인 추적이 어려워진다. 이미 알려진 취약점이므로 먼저 닫는다.

**D-2가 D-3보다 먼저인 이유:** C2 이탈 규칙(생존자 소지품 확정)은 **개별 탈출의 전제 조건**이다. 순서를 뒤집으면 그리핑 가능한 상태가 중간에 생긴다.

**D-4에서 한 번 출시 가능한 상태가 된다.** 공개 매칭 없이 IP 직접 연결만으로 게임이 성립하므로, D-5 이후는 시점을 따로 잡을 수 있다.

**C5(입장 payload 검증)를 D-6에 둔 이유:** 친구·커뮤니티 서버 경로에서는 필수가 아니고, 우리가 여는 공개 매칭에서 전제 조건이 된다.

A(서버 타깃)는 나머지와 독립적이라 먼저 손대도 무방하다. 다만 A2에서 렌더 모듈이 서버 타깃 빌드를 통과하는지가 첫 관문이다.

**실제 비용의 대부분은 D-1~D-3(공통 기반)에 있다.** 호스팅 모델 선택이 아니라 개별 탈출과 멀티플레이 기반 정리가 큰 작업이다.

## 출시 방침 재검토 트리거

로컬 `SaveGame` 영속을 유지할 수 있는 조건은 **"내 조작이 남에게 영향을 주지 않는다"**이다. 아래 항목이 켜지면 그 전제가 깨지므로 저장 방침을 다시 판단한다.

| 트리거 | 상태 | 대응 |
|---|---|---|
| 모르는 사람과의 공개 매칭 | **켜짐** | 공개 경로는 데디(E2) + 입장 검증(C5)으로 완화 |
| PvP | 꺼짐 | 켜지면 백엔드 경제 권위 필요 |
| 플레이어 간 아이템 거래 | 꺼짐 | 켜지면 백엔드 경제 권위 필수 |
| 랭킹·리더보드 등 공유 지표 | 꺼짐 | 켜지면 서버 검증 필요 |

공개 매칭은 이미 켜졌지만, PvE 코옵이라 위조 로드아웃의 피해가 "판이 시시해진다" 수준에 그쳐 **데디 + 입장 검증으로 완화 가능**하다고 판단했다. 나머지 셋 중 하나라도 켜지면 완화로 부족하며 [SaveBackendMigration.md](SaveBackendMigration.md) 3단계(백엔드 경제 권위)가 필요해진다.

특히 **플레이어 간 거래**가 결정적이다. 거래가 생기는 순간 위조 아이템이 남의 계정으로 흘러들어가 경제 전체를 오염시키므로, 완화책으로는 막을 수 없다.

```text

- C4  공개 매칭의 최소 인원 / 대기 정책
- C7  탈출한 플레이어에게 로비 UI 오버레이를 줄지 (대기 시간을 로비 시간으로)
```
